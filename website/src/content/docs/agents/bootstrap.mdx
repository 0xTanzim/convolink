## Start with onboarding

On a fresh project, do not guess which browser or profile is configured. Run onboarding
to get the current state and one next action:

```bash
convo onboard --json
# fresh machine without a global install? identical binary:
bunx convolink@latest onboard --json
```

```json
{
  "ok": false,
  "command": "onboard",
  "data": {
    "transport": "extension-bridge",
    "port": 9224,
    "steps": [
      { "id": "daemon", "status": "done", "summary": "Daemon answering at http://127.0.0.1:9224" },
      { "id": "extension", "status": "todo", "summary": "No companion extension has connected to the bridge.",
        "action": { "kind": "user", "instruction": "Follow the browser-specific setup instruction …" } },
      { "id": "profile", "status": "todo", "summary": "No .convo/config.json for this project yet." },
      { "id": "transport", "status": "blocked", "summary": "extension-bridge is not answering." }
    ],
    "nextAction": { "kind": "user", "instruction": "…", "why": "The selected browser setup needs a user action." },
    "requiresUserSelection": { "question": "Which browser profile should ConvoLink drive for this project?", "options": ["Personal <you@example.com> (chrome)"] },
    "warnings": []
  },
  "error": { "code": "not-ready", "message": "…", "remediation": "…", "retryable": false }
}
```

`nextAction.kind` decides who acts:

| `kind` | Who | What to do |
|---|---|---|
| `command` | the agent | Run `nextAction.command`, then call `onboard` again |
| `user` | the human | Print `nextAction.instruction` verbatim and stop |
| `tool` | the agent | Call that MCP tool with `nextAction.args` |

Repeat onboarding after completing each action until `ok: true`. Do not keep retrying a
step that explicitly requires the person using the browser.

## Why not just edit `.convo/config.json`?

Because the profile is the human's decision. Picking one silently is how a project ends up
driving the wrong browser session. `onboard` returns the choice set; the user picks; the
config is written by `convo profile select` — never by hand.

<Aside type="caution" title="Do not silently switch browser profiles">
An automation profile is separate from an everyday profile and may not have the same
cookies or signed-in AI sessions. Ask which profile to use before changing the project
configuration. For Chrome-family everyday profiles, the Companion Extension avoids debug
flags; Firefox and Zen can use native BiDi.
</Aside>

## Transport: pick once

| Situation | Transport | Port |
|---|---|---|
| Chrome / Brave / Edge / Chromium, user's profile | `extension-bridge` | `9224` |
| Dedicated automation profile, headless, CI | `raw-cdp` | `9222` |
| Firefox / Zen | `firefox-bidi` | `9223` |

Chrome 136 and newer require a non-default user-data directory for CDP. For an everyday
Chrome-family profile, use the Companion Extension. For Firefox or Zen, use native BiDi.
See [browser connection setup](/convolink/getting-started/browser-connection/) for the
full transport comparison.

## First real call

```bash
convo doctor                     # transport, tabs, selector health
convo list --json                # target ids
convo ask "reply with: ok" -p chatgpt --transport extension-bridge --json
```

Then read [the setup contract](/convolink/agents/setup-contract/) for every exit code, and
[install the skill](/convolink/agents/skills/) so the agent knows this without being told.
